# 16 · 硬件与系统基础

> 目标：能沿着“磁盘 → 内存 → CPU → 加速器 → 网络”解释一次训练或推理的时间花在哪里，并用测量选择优化方向。先修：Python、数组与张量、基本命令行；少量 C 有帮助。学习规划预算约 120–220 小时。普通电脑即可完成。
> 时间口径：具备先修后，系统学习主教材、完成练习与一个项目的规划预算；不包含补先修，也不等于掌握整个领域。实际投入受基础、实验条件和项目深度影响。

AI Infra 的起点是理解数据如何移动。矩阵乘法只是请求的一部分；读取样本、解压、分词、分配内存、传输、排队，都可能让计算单元等待。本章不要求先造一台计算机，而是建立能解释真实程序行为的系统模型。

## 学习顺序

1. **数据表示与执行**：整数溢出、浮点误差、指针、进程与线程；理解 Python 调用数值库时，计算可能发生在本地编译代码中。
2. **存储层次**：缓存行、局部性、DRAM、虚拟内存与页缓存；比较连续访问和跨步访问。
3. **操作系统与 I/O**：调度、锁、阻塞、文件布局、预取；画出一个数据加载管线。
4. **网络与性能诊断**：延迟、带宽、TCP、连接复用、队列；建立基线后再调并发。
5. **综合实验**：提交一份有原始测量和反例的性能报告。

## 把概念连成一条数据路径

**容量、带宽、延迟回答三个不同问题。** 容量决定“放不放得下”，带宽决定“大量数据搬多快”，延迟决定“一次请求多久开始得到结果”。假设连续读带宽为 1 GiB/s，搬运 4 GiB 至少需要约 4 秒；但读取一百万个小文件时，文件打开、元数据访问与随机读取可能主导时间，此时换一块标称顺序带宽更高的盘未必有效。这是教学估算，不是任何硬件的实测成绩。

**缓存让访问方式成为算法的一部分。** 程序访问一个元素时，硬件通常搬入一整条缓存行。接下来访问相邻元素能复用已经搬来的数据；跨大步长跳转则可能只使用每条缓存行的一小部分。矩阵分块的价值，是把即将重复使用的小块留在更近的存储层。计算复杂度同为 O(n³) 的矩阵乘法，实现速度也可能不同。学习入口是 [CS:APP 作者站](https://csapp.cs.cmu.edu/)的内存层次与程序优化内容。

**虚拟内存不是免费增加的物理内存。** 一个进程可以拥有很大的虚拟地址空间，实际驻留内存却小得多。缺页可能只需要建立映射，也可能触发磁盘读取；内存压力还会造成回收和换入换出。页缓存能让第二次读文件明显快于第一次。NUMA 机器上，访问另一插槽附近的内存可能增加代价，因此“总内存够用”不能保证访问高效。[Linux 内存概念文档](https://docs.kernel.org/admin-guide/mm/concepts.html)解释了这些区分。

**并发能够覆盖等待，也会引入争用。** 数据加载线程可以在 GPU 计算时准备下一批数据；但增加 worker 数量也会增加进程间传输、内存副本、磁盘随机访问或锁竞争。有效优化要画出时间线，确认准备数据和计算确实重叠。异步 API 提交完成，也不代表设备上的计算已经结束。

**整体速度受到未优化部分限制。** 若 70% 的原始时间用于计算，计算加速 8 倍，其余不变，则 Amdahl 定律给出：

$$
\text{speedup}=\frac{1}{(1-p)+p/s}=\frac{1}{0.3+0.7/8}\approx2.58
$$

这解释了为什么换更快的 GPU 后，端到端训练不一定获得相同比例的提速。先把“等待数据”和“设备计算”分开测量，比直接追求 GPU 利用率数字更有用。

## 核心知识表

| 层次 | 需要理解 | 在 AI 工作负载中的表现 | 首要观察量 |
| --- | --- | --- | --- |
| CPU 与缓存 | SIMD、局部性、缓存失效 | 分词、预处理、数据增强 | CPU 时间、缓存行为、热点函数 |
| 内存与 OS | 进程、线程、页缓存、NUMA | worker 复制数据、内存抖动 | 驻留内存、缺页、上下文切换 |
| 磁盘与对象存储 | 顺序/随机 I/O、分片、压缩 | 小文件拖慢训练、远端读取等待 | 吞吐、请求数、等待时间 |
| 数据格式 | 行式/列式、投影、批量读取 | 只取部分特征或扫描整批样本 | 实际读入字节、解码时间 |
| 网络 | RTT、拥塞、重传、连接复用 | API 尾延迟、节点间同步 | 吞吐、RTT、错误、队列 |
| 系统测量 | 墙钟/CPU 时间、预热、分位数 | 单次测试与线上表现不一致 | p50/p95、重复次数、条件 |

列式格式适合按列读取和压缩，但不等于所有训练数据都应改成 Parquet；图像原始字节、随机样本访问和流式序列化有不同需求。[Parquet 官方概览](https://parquet.apache.org/docs/overview/)适合用来理解格式，而不是作为通用性能承诺。

## 实践：找出一个数据管线的瓶颈

创建小规模合成数据，初次实验控制在数百 MB 内。无需下载模型，也不需要购买 GPU。

1. 写一个“读取 → 解析 → 简单数值计算 → 汇总”的脚本，分别记录每阶段墙钟时间、输入字节数与样本数。
2. 固定总数据量，比较一个大文件和多个小文件；记录文件数量与文件大小，避免只记录一句“更快了”。
3. 对同一输入重复运行，区分首次运行与后续运行。不要为了测冷缓存而随意执行系统级清缓存命令；将缓存影响写进限制说明即可。
4. 比较串行和 2、4 个 worker。保持输入与结果一致，观察哪一阶段变快、哪一阶段恶化。
5. 提交一页报告：实验条件、阶段耗时表、一个瓶颈判断、一项修改、修改前后数据，以及一个无收益的尝试。

**验收**：输出结果一致；每种配置至少运行 5 次并报告中位数；能用计算解释理论搬运下界；能指出至少一种结果受到缓存、并发或系统负载影响的可能性。无需达到固定加速倍数。

## 常见误区与下一步

- “CPU 使用率低说明 CPU 没问题”：进程可能在等 I/O、锁或单个线程，需结合等待状态。
- “内存越少越好”：缓存占用可能在帮忙；要区分可回收缓存与不可控增长。
- “并行一定更快”：把序列化开销和数据复制算进去再比较。
- “微基准提升就是业务提升”：最终回到整个任务的完成时间和资源成本。
